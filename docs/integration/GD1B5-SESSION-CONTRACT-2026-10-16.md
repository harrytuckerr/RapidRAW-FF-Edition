## 1. Next assignment: one module, truthful stopping point

Own only NEW `src-tauri/src/drive_auth/session.rs` with inline tests and its separately assigned receipt. Root alone exports/registers modules. Implement one native authorization-attempt supervisor using the real loopback and exchange APIs, ending at **AccountVerificationPending**. No Connected/Verified constructor, account HTTP request, browser implementation, IPC command, UI, persistence, refresh, scopes/dependencies or existing-source changes. Start implementation only on a root-frozen snapshot where exchange has passed its independent gate; do not work around a failing candidate.

Four meanings must remain distinct:

| Meaning | Evidence needed |
|---|---|
| Authorization completed | Matching callback + successful code exchange and explicit parsed granted subset; still no verified account |
| Authenticated account verified | Separate fixed authenticated Drive about.get response tied to these exact tokens and trusted native registration |
| Session-only connected | Verified candidate adopted atomically for the current attempt/generation; valid in-memory token; no durable credential claim |
| Drive ready | Account-scoped provider/workspace/access reconciliation for the chosen capability; neither login nor about.get alone establishes this |

The next module may report only the first row and pending verification. Parsed token strings, requested scopes, unknown id_token, email, or a syntactically valid model AccountKey are never proof for later rows.

## 2. Minimal native interface and state

Suggested concrete interfaces (native-only; no Serialize on secret owners):

```rust
SessionController::new() -> SessionController;
async SessionController::begin(&self, request: NativeStart) -> Result<BrowserLaunchTicket, StartError>;
SessionController::snapshot(&self) -> Result<AuthSnapshot, ControllerError>;
SessionController::cancel(&self, attempt_id: Uuid) -> Result<CancelDisposition, ControllerError>;
SessionController::invalidate(&self, reason: DisconnectOrSwitch) -> Result<(), ControllerError>;
async SessionController::shutdown(&self) -> Result<(), ControllerError>;
BrowserLaunchTicket::url_for_native_launcher(&self) -> Result<&str, TicketError>;
BrowserLaunchTicket::finish(self, result: BrowserHandoff); // HandedOff or Failed only
```

NativeStart contains bounded native registration metadata (client ID, registration ID, configured project number) and a unique nonempty ApprovedScope set. It accepts no endpoint, URL, token, account/email proof or arbitrary credential. Registration/project mapping is trusted application configuration, not inferred from client-ID text. Root later selects the configured registration from a safe IPC capability request; JS must never supply an auth URL.

SessionController is the non-Clone owner; tasks hold a separate Arc<Inner>, not Arc<SessionController>, so task references cannot prevent owner Drop. Inner has one std Mutex protecting: closed latch, checked u64 generation/sequence, one attempt ID, phase, cancellation senders/handle, optional pending ExchangeResult, and one last authorization outcome. No growing history/event queue. A native tokio watch snapshot may carry only bounded metadata/status/scopes, never URLs, codes or tokens. Watch is a notification; snapshot is authoritative. Future IPC uses canonical UUIDs and decimal-string counters, not lossy JavaScript numbers; no serializer is required in this first native-only slice. Poisoned state/counter overflow fails closed, cancels work and rejects new admission; no reset-to-zero or poison recovery that permits adoption.

One slot includes startup, active work, pending verification **and draining cleanup**. A second begin returns Busy without changing the incumbent's phase, generation or status. No implicit cancel-on-start. Explicit cancel/disconnect/switch first invalidates the current generation under this same mutex and signals workers; the slot is reusable only after owned resources are reaped. UUID+generation checks also apply to late startup/browser/worker completion, not just token adoption. A stale attempt-specific cancel is inert. Disconnect/switch drops this module's pending secrets, never edits photos/settings/libraries or revokes Google access. First slice has no existing verified session to mutate; later verified-session storage must join this same commit boundary, not introduce a competing lock.

No lock across socket binding, browser calls, network futures or awaiting joins. Under lock reserve/copy control metadata or move owned work; unlock to act; relock to conditionally commit. State commit requires !closed, matching ID+generation, nonterminal expected phase, uncancelled status, unexpired overall deadline and valid token expiry. Unmatched results are dropped. In the first slice commit stores ExchangeResult privately in memory as pending, not as connected credentials. No public token getter/"mark verified" method on the controller.

## 3. Worker and browser handoff sequence

Use a single absolute **300-second attempt deadline from admission**, covering binding, browser handoff, callback and exchange. Listener receives the remaining duration (never exceeds its600s limit); exchange retains its30s internal cap and is additionally cancelled by the original attempt deadline. Neither stage change nor invalid local request resets time. Startup/worker-ready budget5s and browser acknowledgment budget10s are subdeadlines, capped by the original deadline. Pending tokens expire at min(token expiry, original attempt deadline); no refresh is attempted.

1. Reserve ID/generation/Starting under lock. Establish a cancellation-on-drop reservation guard so dropping the begin future cannot orphan a reserved attempt. A supervisor owns cleanup even if its caller disappears.
2. Off UI, bind actual `LoopbackSession::bind`. Retain the blocking handle through completion. Obtain its cancellation handle and native authorization URL, recheck generation, and launch `wait_on_worker()` on a blocking worker. A wrapper sends a oneshot ready acknowledgment immediately before entering that method; do not offer the browser ticket until the bound listener's worker has started. Late bind/ready after cancellation closes/drops the session, never returns a ticket for the new generation.
3. Publish exactly one non-Clone/non-Debug/non-Serialize BrowserLaunchTicket containing the native URL, attempt binding and one-shot acknowledgment sender. Its URL accessor checks current identity/deadline. Dropping the ticket or sending Failed terminates browser handoff; no success default. The adapter must claim/check the ticket immediately before calling the OS outside the lock. Cancellation can still race OS launch: the browser may open late, but the old callback/result cannot be adopted.
4. Browser HandedOff means only OS-launch handoff. While awaiting acknowledgment the listener is already pumping. If a valid callback arrives first, retain at most one native grant/outcome; do not exchange the code until a matching successful browser acknowledgment. Failed/missing/late acknowledgment drops that grant, cancels the listener and produces BrowserUnavailable/TimedOut. Never replay it. A callback is not proof that a particular browser API succeeded.
5. After handoff, callback denial/provider error becomes a bounded terminal authorization outcome. Code runs `exchange_code` with the same UUID/generation and an owned oneshot cancellation sender. Cancellation or sender drop cancels it; outer timeout also signals and drops owned exchange work. A successful native result is checked and stored under the commit mutex as AccountVerificationPending. Request acceptance/browser handoff/queued work is never terminal authorization success.
6. Keep pending tokens privately until a later verifier integration consumes them, explicit discard/invalidation, expiry or shutdown. A single deadline watchdog clears expired pending material. Begin remains Busy while pending; no automatic new login or token use. Store only one immutable last authorization outcome: CompletedPendingVerification is final for that authorization attempt; later pending expiry/discard changes retention state without rewriting it into a second authorization result/toast.

Other terminal outcomes: Denied, Cancelled, TimedOut, BrowserUnavailable, bounded Setup/Listener/Exchange/WorkerFailure, Closed. Record once per matching attempt under lock, then notify outside it. Error text is static; never forward browser/OS/reqwest/provider strings. No code/state/verifier/token in status, logs, Debug or IPC.

**Cleanup fence:** cancellation calls the actual loopback Cancellation::cancel and signals/drops exchange/launch channels, then the supervisor joins its workers. Started spawn_blocking work is not abortable. If OS binding/launcher internals do not return, report the terminal cancellation/timeout but retain Draining and reject new starts instead of leaking additional workers or claiming hard release. Explicit shutdown awaits cleanup without holding the mutex; Drop invalidates and signals synchronously, leaving the already-owned supervisor to reap. No task-reference cycle, detached unbounded task list or promise that Drop can synchronously join a stuck OS call. The browser adapter must retain its launch operation until acknowledgment/drop, even after user cancellation; its late completion is inert. Browser windows are not forcibly closed.

## 5. Separate authenticated about.get verifier and adoption

Later NEW `drive_auth/account.rs`, separately assigned/reviewed: one fixed verified-HTTPS GET to `https://www.googleapis.com/drive/v3/about` with a fixed fields projection `user(permissionId,displayName,emailAddress),storageQuota` and Authorization Bearer from the **owned current ExchangeResult**, never a query token or caller endpoint. Reuse the explicit transport policies/bounds conceptually, without changing exchange.rs or inventing a generic HTTP framework: no redirects/proxies/decompression, finite request/deadline/cancel, bounded JSON64KiB/depth/fields, duplicate decoded critical keys and status200 required. A future narrow integration grant lets session move the pending result into this verifier; it does not expose it through IPC.

`verify_account(owned ExchangeResult, trusted NativeRegistration, cancellation) -> Result<VerifiedSessionCandidate, AccountError>` creates the only production proof wrapper. Fields private, no public/default/deserializable/mock "verified account" constructor. Wrapper owns the exact ExchangeResult, registration binding and returned account key, so a caller cannot combine accountA's proof with accountB's tokens. Test constructors may exist only inside cfg(test), never an application API. A parser of raw JSON alone must not return this proof type.

Identity is configured project number + authenticated `user.permissionId`; use existing model syntax primitives after validating a nonempty bounded ID. `AccountKey` at model.rs:213 is explicitly syntax-only and cannot substitute for this network proof. Project/client membership comes from the trusted native registration record, not about.get or a guessed client-ID prefix. Email/display name are optional bounded display metadata, never keys or authentication tests; absence of email is allowed. Missing/invalid user/permissionId, 401/403, partial/malformed response, token expiry or stale generation fails without adopting/replacing credentials. Quota absence or unlimited quota is not identity failure. Do not broaden scopes to repair verification failures.

After verifier acceptance, a separately granted small session integration adds ConnectedSessionOnly. Under the **same commit mutex**, require current attempt/generation/registration, unexpired owned tokens and matching verification candidate. Same-account reconnect may replace the prior native session atomically; reduced scopes replace the old usable set, never union it. A different verified account requires an explicit native switch intent/confirmation bound to that candidate; never replace an existing session merely because the browser selected someone else. Cancel/failure leaves a prior still-valid session intact unless the user explicitly disconnected/switched; local edits always remain intact. Account-switch invalidation stops the old account's future leases/views before new adoption; those Drive-job integrations are later grants. No revocation or code replay as cleanup.

Public Google docs checked 2026-10-16 Melbourne: [about.get](https://developers.google.com/workspace/drive/api/reference/rest/v3/about/get) requires fields and permits both approved appdata and file scopes; [About.user](https://developers.google.com/workspace/drive/api/reference/rest/v3/about) is the authenticated user; [User](https://developers.google.com/workspace/drive/api/reference/rest/v3/User) defines permissionId and warns email may be absent. These docs support the verifier design, not live cross-client/account/scopes acceptance. Actual account verification proves neither workspace readiness nor original-photo availability.
