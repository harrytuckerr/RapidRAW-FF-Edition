## Ownership, cancellation and completion

The existing controller has a 5-second startup budget, **10-second browser handoff budget** and 300-second admission budget. Preserve them; add no renewed timeout. An unpolled/dropped hand_off future owns and drops the ticket without launching. Once dispatch starts, exactly one blocking worker owns the ticket and launcher cleanup; caller-future Drop only requests cancellation. No caller Drop/timeout may destroy a worker-owned ticket, abort a started worker or release its acknowledgment before actual child cleanup.

Use a once-only Pending/Cancelled/Completing atomic decision (or equally explicit reviewed equivalent): caller Drop competes with worker final completion; completion that wins is final. Positive acknowledgment requires successful selected-child exit/reap, cancellation not winning, and the existing current ticket check/consuming finish. Spawn/nonzero failures are failure, stale/expired finishes remain inert. Explicit controller cancellation is still serialized by the existing mutex. A launch can race cancellation after its last pre-dispatch check; do not promise external OS launch can be undone.

A cleanup guard must own both the child and ticket, and be installed before any path can unwind with a started child. Reap/destroy actual launcher resources before finish/drop releases the ticket. Unknown wait/reap failure retains the bounded cleanup fence, even indefinitely; do not drop the child handle and claim completion. A stuck OS operation leaves Draining/Busy and shutdown pending. Do not kill a browser or detach an unbounded task list. No lock across await. No positive browser-load/login assertion from launcher exit; HandedOff means only the selected OS launcher reported success.
