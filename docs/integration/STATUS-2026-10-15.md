## What the integration preserves

Camera-specific DCP bases are installed separately from XMP image Looks. A Look is selectable only when its required base is installed for the image's camera. The selected base and Look run before ordinary editing controls and opt-in preset profile capture; the Look is not treated as an ordinary adjustment preset.

The shared production route is camera-native RAW -> CPU DCP -> native RGB Look -> one conversion from linear ProPhoto to linear sRGB -> upstream image adjustments. Preview, export and thumbnail paths use the shared profile helper. Clearing a profile restores the pristine upstream-developed source. Missing, malformed or incompatible selections error rather than silently reverting to an unprofiled image.

Production profile processing is currently CPU-based. Its GPU request explicitly disables the separate DCP shader stage to prevent double application. The optional shared DCP shader has hardware parity tests, but the profile browser does not activate it in production.

Upstream Kelvin white balance, guided filters, baseline/highlight exposure, Apple RAW 9, metadata/export changes and Android dependency changes are retained. Selected DCPs bypass Apple RAW's already-calibrated RGB and use camera-native rawler development. A decoder dimension mismatch requires reopening with Apple RAW disabled rather than misaligning masks/geometry. Linear RAW is explicitly rejected for DCP until its camera-space status is established.

## Material defects found and corrected

| Severity | Finding and consequence | Correction / evidence |
|---|---|---|
| P1 | Existing production preview did not execute the selected profile; export used a different base-only route. | Shared `dcp/pipeline.rs` entry point before ordinary editing; actual desktop RAW/profile/Look exports exercised. |
| P1 | Rawler WB was treated as RGGB, although it is RGBE and the fourth component may be NaN. Calibration can also apply WB internally. | Use validated RGB components, neutral `[G/R,1,G/B]`, and camera-native development with WB owned once by DCP. |
| P1 | Profile output is linear ProPhoto; downstream processing expects linear sRGB. | One explicit working-space conversion after base + Look, with float-range and numerical render checks. |
| P1 | Native XMP RGB table acquisition was not an evaluator. | Implement supported primaries/transfers, tetrahedral interpolation, amount and gamut handling using Adobe SDK reference structure. Unsupported variants error. Adobe fidelity remains unverified. |
| P1 | Profile changes could reuse stale spatial/pixel caches. | Base, Look and Amount participate in preview, patch and geometry keys; regression tests cover invalidation. |
| P1 | The real Look-pairing response serialized its base ID as 32 bytes, while the frontend and renderer expected hex. CLI tests bypassed this boundary. | Canonical hex serialization, strict legacy-array reads, normalization of sidecars/presets, and tests using the actual `PairingState::Satisfied` type. Android read-back confirms a legacy array becomes hex on save. |
| P1 | Preview errors dropped the response channel and were suppressed as cancellation, leaving stale pixels. | Explicit success/error responses, separate supersession, current-request visible errors and stale-request guards. |
| P1 | Android's selected GLES adapter exposed zero compute storage limits, producing invalid pipelines. | Prefer Vulkan by default on Android; validate actual capabilities and resource limits before creating pipelines. Respect explicit backend overrides. |
| P1 | The initial limit fix requested one storage texture, but the combined flare layouts require two. | Corrected requirement and a real full-processor hardware test covering both precision modes. |
| P2 | Touch profile picker was clipped and autofocus opened the keyboard over its choices. | In-flow mobile/coarse-pointer picker, no automatic touch focus, readable disabled-pair explanations. Exercised through real touch input. |
| P2 | Preview handling ignored valid JSON-byte fallback responses from Tauri. | Validate and normalize ArrayBuffer, Uint8Array and numeric-byte responses. The compatibility gap is source-confirmed; its contribution to the observed emulator failure is not established. |
| P1 | Malformed XMP could loop at EOF; table inflation needed bounds. | Explicit EOF errors, bounded decompression and invalid-grid rejection. |

Frontend capture fixes also retain zero Amount, avoid unintentionally capturing profiles in ordinary presets, and guard stale camera/profile requests. Android JNI uses a retained application reference instead of a replaceable Activity reference.

## Remaining P1 blocker: Android graphics pipeline creation

Environment: `emulator-5584`, ARM64 Android API33, WebView 101.0.4951.74, Vulkan `SwiftShader Device (LLVM 10.0.0)`. This is software graphics inside an emulator, not a physical Android GPU.

Final diagnostic APK SHA-256:
`bf8d139932aba062ec4da0d8ffcf446d6465ecec96b258dd658e5aace018a546`.

The final log records:

1. Camera-native RAW development completes.
2. DCP renderer and native Look prepare successfully; working RGB pixels complete.
3. The GPU preparation poll returns.
4. `GpuProcessor::new` enters `Horizontal Blur Pipeline` and never records its exit during the observation window.

The first blur shader is byte-identical to upstream `3385c9f0`. Its resource requirements fit the requested device limits. Upload, guided filtering, main dispatch and readback have not been reached by that construction. Source review found no relevant application lock cycle. Native debugging did not yield a usable stack.

The leading hypothesis is a wgpu/Vulkan–SwiftShader pipeline-compilation compatibility issue. The evidence does **not** conclusively identify an internal driver or compiler fault, nor prove unmodified upstream Android has the same runtime failure. Do not alter colour math or weaken validation to turn this test green.

Earlier visible original pixels were not evidence that edited rendering worked. Image-region comparison showed zero pixel change after profile selection; the later diagnostic isolated the blocked stage. This corrects the earlier provisional interpretation.

Reproduction: install the final APK; import the generated synthetic RAW, matching base and Look through SAF; open the RAW and select the Look at 100%. The retained test installation reproduces this with its saved edit. See `evidence/android-final-diagnostic.log`, `evidence/android-final-result.json` and the attempt-8 build/source receipts.

## Fidelity and performance limits

Nonzero native Looks clamp finite pre-Look ProPhoto channels to [0,1]; Amount 0 bypasses exactly. This is an explicitly bounded, non-HDR adaptation, not reproduction of Adobe's preceding exposure/tone pipeline. Captured-table and unsupported variants error. Adobe ΔE acceptance remains open.

The production path redevelops camera-native pixels for selected profiles. Interactive performance on full-resolution commercial camera scenes has not been measured. One synthetic upstream comparison is not broad camera regression coverage. Apple decoder dimension changes and linear RAW remain explicit restrictions.
