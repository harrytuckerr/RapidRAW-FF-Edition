## Important corrections to inherited assumptions

- The historical production preview did not activate DCP; export used a different base-only path. Both now need the same camera-native -> profile -> working RGB entry point before ordinary adjustments.
- Rawler metadata WB is RGBE, not RGGB. The fourth entry can be NaN for RGB sensors. DCP needs the first three components and finite-positive validation.
- Rawler performs WB inside calibration. Removing calibration bypasses it; the DCP renderer must own WB exactly once.
- DCP render_pixel/render_slice returns linear ProPhoto. Production downstream expects linear sRGB. Conversion must occur once, after profile processing.
- The supplied XMP Looks contain RGB tables, not the DCP HSV table representation. Decoding does not prove amount, gamut, interpolation or transfer evaluation is implemented.
- Earlier no-profile and ACR acceptance tests were incomplete. A synthetic identity check is not a comparison with upstream or Adobe.

## Integration contract

- Production profile processing uses the shared CPU entry point before existing GPU editing. CPU-profile output uses `has_dcp=0` and no DCP GPU textures, avoiding double application. The optional DCP shader path remains separately tested, not claimed as the active production profile route.
- Upstream guided filters retain GPU bindings 12/13; DCP resources move to 14/15/16 with matching host layouts.
- Profile identity/Look/Amount participates in patch and geometry caching as well as the preview transform cache.
- Apple RAW 9 output is already working RGB. Selected DCPs route through rawler camera-native development. If switching decoders changes loaded dimensions, request reopening rather than applying misaligned masks/geometry.
- Linear RAW is rejected for DCP until its camera-space status is established. File extension alone does not prove sensor RGB.
- Default/no-profile rendering is compared against the NEW upstream baseline, not August output that upstream deliberately changed.
- Android uses a separate pinned dependency copy. Desktop lockfiles are not downgraded.

### Native Look rendering limits

The evaluator follows the cited Adobe SDK reference structure for RGB table acquisition, tetrahedral interpolation, transfer functions, amount and gamut treatment. Production adaptation deliberately clamps finite pre-Look ProPhoto channels to [0,1] at nonzero Amount; Amount 0 bypasses exactly. This is not a claim to reproduce Adobe's preceding exposure/tone stages or HDR/scene-referred rendering. Captured tables, unsupported table variants and missing/incompatible profile selections error explicitly.

The supported production path is CPU profile processing before upstream GPU adjustments. Hardware DCP parity validates the optional shared shader; it does not mean the profile browser currently activates that shader in production. Interactive performance on full-resolution real-camera scenes remains to be measured.

### Test honesty

The real upstream comparison above was performed externally on actual application executables; it is a single controlled fixture, not a broad camera matrix or an automated CI golden corpus.

## Android runtime corrections

Actual device execution caught defects that APK compilation did not: the selected graphics adapter exposed zero storage texture/buffer limits, producing invalid pipelines and a black editor; the absolute profile dropdown was clipped and automatically opened the keyboard. Android now prefers Vulkan unless explicitly overridden, rejects insufficient compute capabilities before constructing invalid pipelines, and logs the selected adapter. The mobile picker expands within the scrolling controls and avoids automatic keyboard focus.

Independent review caught that flare processing combines two storage-texture bind groups; the requested device limit must be at least two, not one. The correction is included. A complete processor-construction hardware test is being added; shader-only parity did not cover this failure.

### Profile IPC mismatch caught by Android interaction

The first real paired-Look selection exposed a wire contract mismatch: camera browser entries use hex IDs, but `PairingStatus::Satisfied.base` serialized the `ProfileId([u8;32])` as a byte array. Selecting a Look overwrote the valid base selection with that array, and the shared renderer correctly rejected it. CLI fixtures used explicit hex IDs, so their successful renders did not test this boundary. The preview worker dropped actual errors and the frontend treated channel closure as quiet supersession, retaining stale pixels.

Implemented; runtime retest pending: canonical hex serialization with legacy array reads; targeted normalization for saved generic-JSON selections; real browser/pairing serialization regression coverage; explicit error response separate from supersession and visible current-request failures. Android paired-Look visual acceptance remains blocked until this is retested.
