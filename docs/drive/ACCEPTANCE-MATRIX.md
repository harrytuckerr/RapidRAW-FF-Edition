# Google Drive cross-device acceptance matrix

This matrix records the approved user scope and concrete acceptance evidence against the frozen GD0 contract. The contract is an implementable model, not provider, security, policy, product, or operational acceptance. Contract-derived expectations below are test targets; they do not prove the provider will honor app-data sharing or that profile-library sync is policy-eligible for distribution. Every case starts **Not exercised**. Source inspection, mocks, and builds do not count as live provider, cross-device, or physical-device acceptance.

## User scope

For the same Google account, settings, saved edits, named checkpoints, presets, and selected, legitimately user-imported profile libraries are intended to be available on desktop and Android. Under the frozen model, settings and enrolled saved state use private `appDataFolder` only after separate `drive.appdata` consent; the visible photo workspace uses `drive.file` consent. These spaces and consent categories must remain distinct. Photos are downloaded on Open/Keep local and original upload is separately explicit; full automatic photo backup is out of scope. A photo not available locally must show Locate original / Add original to Drive, not a blank success. Device-local paths and performance/backend choices stay local, and editing remains usable offline. User-authorized imported profile bytes and preset state may sync privately, but must not leak into Git, application packages, or rendered image exports. Do not sweep Adobe/system directories or infer consent from discovery. Public distribution and actual cross-client grant/profile-library policy fit remain unproven.

## Shared evidence required

For live/provider cases, record the exact application source revision and desktop/Android artifact identifiers, platform/client registration used, fresh granted scopes, test account label (redacted), source and transferred object hashes/IDs, and redacted errors. For device cases, record actual device/model/OS and the user-visible action. Preserve original test assets and working files. Do not include passwords, access tokens, resumable session URLs, photo bytes, or other credential values in evidence.

## Registration and test inputs still unknown

Live acceptance needs owner-controlled Cloud project ID and number, enabled Drive and Picker APIs, consent-screen public details and URLs/domains, test/production audience, desktop OAuth client IDs and approved loopback configuration, Android client ID bound to package and actual signing-certificate SHA-1 for each tested build, and authorization for designated test account(s). Workspace restrictions and fresh grants for appdata-only, file-only and combined consent must be confirmed. Exact identifiers and account values belong only in redacted controlled receipts; passwords, access tokens, callback values and resumable URLs must never be requested or recorded. Device cases also need exact application artifacts, physical device/OS details, designated synthetic JPEG/RAF and licensed-for-test profile/preset fixtures, and controlled network/storage conditions. Missing inputs block only the corresponding live cases; they do not turn source/mock/build evidence into a pass.
