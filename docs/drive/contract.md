## 1. Decision and authority

Prioritise Drive before the E additions. Deliver cross-device **settings, saved edits, named checkpoints, presets and legitimately user-imported profile libraries**, with photos downloaded only when needed. Desktop and Android use the same Google account; local/offline editing stays independent. The latest task/user scope supersedes the older research §7/§12 and handover §16 exclusions of edit sync/profile upload and their older sequencing. Their least-privilege, preservation and evidence rules still apply. Do not reinterpret profile transfer as export embedding or automatic vendor-directory collection.

V1 is a personal My Drive workspace with explicit initial category enrolment, then background reconciliation of enrolled saved state while the app/OS permits. No automatic original-photo backup, original replacement/deletion, shared-drive support, external recursive folder discovery, backend photo relay, new renderer, or always-running desktop daemon. Existing-file selection is a Google Picker permission step, not the everyday gallery. Initial sync presents local-versus-cloud differences; it never bulk overwrites either side. Photos may remain local-only; another device then receives edits but shows **Locate original / Add original to Drive**, not a blank success.

Use `https://www.googleapis.com/auth/drive.file` for the visible photo workspace. It covers app-created files and selected existing files. Same-project cross-client consent makes a common app-owned workspace plausible; **cross-client file grants, private properties and rediscovery remain unproven**. Selecting a folder does not establish recursive authorization. No scope escalation to fix a failing test. [Scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth), [cross-client identity](https://developers.google.com/identity/protocols/oauth2/cross-client-identity).

**Chosen state store:** request the additional non-sensitive `https://www.googleapis.com/auth/drive.appdata` explicitly for Settings + saved-state/checkpoint + preset/profile-library sync; request drive.file separately when connecting photos. `appDataFolder` is app-specific, hidden from ordinary Drive UI/other apps, cannot share/trash/move objects across spaces, and can be deleted by the user. It is appropriate for configuration and internal manifests; using it for internal editing dependencies is a design inference requiring the policy and fresh-client tests below. It does not replace the visible photo workspace. Do not treat it as the only recoverable copy: keep durable local state and provide explicit local recovery export. [Application data semantics](https://developers.google.com/workspace/drive/api/guides/appdata).

A drive.file-only design with visible state objects is technically plausible, but exposes internal configuration/library files to ordinary folder handling; v1 chooses appDataFolder isolation instead. No silent fallback or data migration between spaces. Settings-only consent must work without photo access. Test both scopes independently, then together; declining photo consent must leave settings sync/local editing usable.

**Distribution gate:** current Google policy explicitly excludes “Backup of user or app content from a developer's app or project to Drive” and constrains retained cached Google data. This does not establish that user-operated photo editing/configuration sync is backup. Eligibility of this opt-in editable workspace—including settings/profile sync and retained offline working copies—must be resolved against the actual product before public enablement. This is a material provider-policy question, not a claim that consent or a new label supplies an exemption, and not a veto on the user's expanded scope or pure local implementation. No general backup feature is proposed. [Workspace policy, Drive-use and retention sections](https://developers.google.com/workspace/workspace-api-user-data-developer-policy).

## 3. Native boundaries and v1 DTOs

Wire objects use camelCase, a required `schemaVersion: 1`, UTF-8 JSON and tagged enums. Reject unknown versions, duplicate JSON keys, invalid enums, nonfinite numbers, oversize values and path/URL fields where not specified; retain incompatible downloaded bytes quarantined for recovery, never default them into valid state. All hashes are lowercase 64-hex SHA-256 unless explicitly named `dcpBlake3Id`. UUIDs are canonical UUID strings. Byte counts, sequences and provider versions cross JS as unsigned decimal strings (no precision loss). Native newtypes enforce ranges; human names are at most 256 Unicode scalars. Parent sets are unique and bounded to 32; larger conflicts stop for staged resolution, not truncation.

```text
AccountKey = {projectNumber, drivePermissionId} // validated about.get user; NOT email/client ID
Connection = {schemaVersion, accountKey?: AccountKey, generation: UUID, clientRegistrationId,
              state: disconnected|authorizing|connected|reconnectRequired|blocked,
              grantedScopes: [string], displayEmail?: string, workspaceId?: UUID}
Workspace = {schemaVersion, workspaceId, accountKey, stateSpace: appDataFolder,
             photoRoot?: {rootFolderId, photosFolderId, exportsFolderId}}
BlobRef = {sha256, bytes, kind: profileDcp|profileLook|lut|patch|mask|watermark|state|originalPhoto|renderedExport}
RemoteLocator = {space: drive|appDataFolder, fileId, observedVersion, resourceKey?: string} // native, not a path
MediaIdentity = {mediaId: UUID, bytes, sha256?: string, formatHint, variantId: UUID}
AssetRef = {schemaVersion, accountKey, workspaceId, media: MediaIdentity,
            remote?: RemoteLocator, availability: onlineOnly|local|unavailable|changed}
LocalBinding = {accountKey?, workspaceId?, mediaId, variantId,
                localObjectId: UUID, verifiedSha256, verifiedBytes} // paths private in native store
RevisionRef = {revisionId: UUID, sha256}
Revision = {schemaVersion, workspaceId, objectId, kind, revisionId: UUID,
            parents: [RevisionRef], deviceId: UUID, deviceSequence,
            createdAt, engineContract: string, payload, dependencies: [BlobRef],
            requiredRevisions: [RevisionRef]} // cross-object refs separate from ancestry
TransferJob = {schemaVersion, jobId: UUID, accountKey, workspaceId,
               operation: putBlob|putRevision|fetchBlob|fetchOriginal|putOriginal|putExport,
               objectRef: BlobRef|RevisionRef|AssetRef, sourceSnapshotId?: UUID, targetFileId?: string,
               state, confirmedBytes, totalBytes, attempts, nextAttemptAt?, error?: DriveError}
CacheEntry = {schemaVersion, accountKey, fileId, observedVersion, sha256, bytes,
              localObjectId, lastUsedAt, expiresAt?, pins: [open|dirty|queued|checkpointDependency]}
StagedExport = {schemaVersion, snapshotId: UUID, mediaId, editRevision: RevisionRef,
                encodedBlob: BlobRef, format, metadataPolicyVersion,
                outputName, localObjectId} // immutable finished encoded file, not pixel JS buffers
DriveError = {code: AuthRequired|Denied|Network|RateLimited|QuotaFull|DiskFull|SourceChanged|
                   MissingDependency|UnsupportedSchema|Conflict|Integrity|ResourceLimit|Io|ApplyFailed, retryable, jobId?, message} // message <=512 scalars; no tokens/URI grants/raw paths
```

Connected state requires a verified accountKey; missing identity cannot authorize a job. Required revisions use the same 32-ref bound as parents. Parents must share object/workspace, form an acyclic graph and match the referenced bytes. `objectId` is workspace-scoped: fixed `settings`/`workspaceBinding`, `edit:<mediaId>:<variantId>`, or kind plus UUID for media/checkpoint/preset/presetFolder/profile library entry/export preset. Duplicate friendly names are legal. `createdAt` is display-only, never ordering authority. Hash the exact serialized revision bytes; no self-hash field inside Revision. Parent refs bind both ID and bytes. Blob/revision remote locators are transport metadata held separately; immutable media records publish the selected original locator for other devices: reuploading identical immutable content may change its locator without changing semantic identity. Hashes prove equality/integrity, not authorship or licensing. Source paths, access tokens and resumable URLs never occur in shared manifests.

Native interfaces: `AuthProvider.authorize(interactive) -> Connection`, `withAccessToken(accountKey,generation,request)` (secret never serializes), `WorkspaceProvider.discover/list/get/createImmutable/downloadRange`, `SyncStore.commitLocal/ingestRemote/listHeads/resolve/leaseJob/ackJob`, `AssetResolver.ensureLocal(AssetRef) -> LocalBinding`, `ExportDestination.enqueue(StagedExport, accountKey, workspaceId) -> jobId`. Commands return durable queued receipts, not “uploaded.” Events carry accountKey+generation+jobId+monotonic sequence; consumers ignore foreign/stale events and reconcile from durable status after listener readiness/restart. Only native validated opaque object IDs resolve to filesystem paths.

## 5. Media identity, durability and conflict rules

A filename, path, timestamp, Drive MIME or preview is never content identity. Before a saved edit can be rendered on another device, require full original SHA-256+length equality. BlobRef kinds originalPhoto/renderedExport are restricted to space=drive; all other v1 sync kinds belong to appDataFolder. MediaId survives renames/moves; variantId distinguishes virtual copies of identical bytes. An unknown hash permits listing/metadata sync with `OriginalUnverified`, never applying edits to a guessed file. User rebinding hashes the selected local file; different bytes require a new media relationship with explicit acknowledgement, not automatic reuse. Drive ID+version identifies an observation; provider metadata-only version changes can be rebound after byte equality. A replacement hash preserves old edits and offers changed-original recovery. Remote 404/removed access means unavailable, not deletion. Download original bytes and run existing content validation; never edit a Drive thumbnail or relabel JPEG-as-RAF.

**Local durability:** one native writer per account store, transaction IDs and immutable staged payloads. `commitLocal` durably commits revision+dependency pins+outbox intent together before returning a saved revision. Use existing dependencies for a checksummed transaction-file journal: same-directory temp, flush/fsync, atomic non-clobber commit, then parent-directory durability where supported. Recovery ignores incomplete uncommitted temps; corrupt committed records stop with recovery status. Replay idempotently reconstructs heads/jobs; no acknowledged save may depend on React lifetime. Platform power-loss guarantees require filesystem fault testing. Preserve legacy files before migration; never replace corrupt state with defaults.

Sync store is authoritative for enrolled objects; existing settings/preset/sidecar files become idempotent local projections with a materialization receipt and revision ID. All enrolled write call sites must use the adapter; otherwise enablement is blocked. Remote apply has origin `remote` and must not echo a new local revision. Failed projection leaves recoverable committed data and `ApplyFailed`; current renderer/UI stays at the prior valid state. Local edits stay durable and locally usable without Google. Transient slider frames are not cloud commits: sync at gesture/save completion and at most one ordinary saved edit revision per image per 5 seconds; named checkpoints/explicit Save flush immediately. Coalesce only never-published ordinary outbox snapshots without children/checkpoint references; never claim coalesced intermediate history existed remotely.

**Protocol:** create immutable blobs first; verify server hash/length (or downloaded bytes when checksum unavailable), then create an immutable revision manifest as the commit marker. No mutable shared “latest.json,” Drive revision-number CAS, or multi-file atomicity assumption. Preallocate and durably record a Drive file ID per create operation; retry/reconcile that ID after ambiguous success. Same revision ID with different bytes is corruption; duplicate files with identical revision bytes deduplicate logically. A manifest with absent dependencies/parents/required revisions is `PendingDependencies`, never applicable. No runnable remote instructions.

Derive heads from validated parent ancestry per object, excluding ancestors of other heads. Ingest is order-independent/idempotent. One descendant head can fast-forward only a clean object; dirty/in-use edits are not replaced. Two incomparable heads, including offline changes or concurrent initial settings, produce `Conflict`. Keep both payloads, local work and provenance. User chooses Keep this / Keep other / Save both (new variant/preset ID) or explicit manual merge. Resolution writes a new revision naming **all observed heads as parents**, with chosen payload; unseen racing heads remain conflicts on the next reconciliation. Wall clock and device sequence never choose a winner. Checkpoints remain separately addressable. Settings/preset membership use the same rules; this is a bounded record-level model, not a generic CRDT.

Enrolment snapshots/overlays are account-scoped and preserve the pre-connection local settings/preset baseline. Remote account state is never written back into that baseline on switch; user-selected local edits remain local and may be deliberately enrolled into a different account later. Local dirty generation is independent of sync status: upload acknowledgement for N cannot clear N+1. UI distinguishes `Saved locally`, `Waiting for network`, `Syncing`, `Synced as of <reconciliation>`, `Conflict`, `Missing dependency`, `Needs reconnect`, `Quota/storage full`, `Apply failed`. An empty/malformed/partial response never means synced. Queue state: queued → running → verifying → complete; pause states user/network/OS/storage/reconnect, plus retryAt/failed/cancelled. Cancellation after uncertain remote completion reconciles first; it never deletes a possible uploaded object.

A tombstone uses the target objectId and its observed heads as parents (not a new unrelated object); it dominates only observed causal ancestors. Concurrent edit versus tombstone is a recoverable conflict. Restore writes a revision descending from tombstone plus the selected prior value; no silent resurrection. V1 performs **no remote garbage collection or permanent deletion**: immutable blobs/revisions/tombstones stay until user-managed provider deletion or a later reviewed retention feature. Keep all local unsynced/conflict/checkpoint data; quota exhaustion pauses sync and reports retained bytes, never prunes the only copy. App-data logical tombstones are never implemented using trash (unsupported there). Local orphan temp blobs may be removed after 7 days only when proven unreferenced by committed/pending transactions. This retention is an explicit v1 limit requiring policy review, not infinite-storage assurance.

## 6. Provider layout, auth and transfers

Store the workspace descriptor, state manifests and dependency blobs as flat appDataFolder children (`parents=["appDataFolder"]`, `spaces=appDataFolder`); private properties identify workspace/role/object/revision. Originals and rendered exports never go there. On separate photo consent, create/discover a visible RapidRAW folder by private app marker, storing account+folder ID, not name; it has Photos/Exports children. The immutable workspace descriptor gains a versioned photo-root binding through a separate `workspaceBinding` configuration revision, not an overwritten descriptor; its record-level conflicts use the same rules. Multiple roots/workspaces require user choice, never automatic merge. Folder rename survives; inaccessible/trash/shared-drive relocation pauses rather than silently creating a replacement. Sync object UUIDs and markers are hints only: validate owner/account/workspace/bytes after fetch. Gallery lists only authorized direct children of Photos/Exports, with generic-RAW MIME support and placeholders; label it **Photos added or authorized to RapidRAW**.

Maintain independent cursors for appDataFolder and drive. For app-data changes do not set `restrictToMyDrive=true`, which excludes that space. Initial reconciliation obtains a change token, enumerates all relevant pages, then catches up from that token; persist each processed page and next cursor atomically. Resume interrupted pages idempotently. Partial results do not delete local records or establish caught-up state. Follow changes while active (60-second default, plus reconnect/manual/after upload); re-enumerate on invalid cursor. No webhook/server requirement. appDataFolder loss keeps local revisions and requires explicit create/recover choice; do not re-upload deleted app data automatically. [files.list](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/list), [change-token lifecycle](https://developers.google.com/workspace/drive/api/guides/manage-changes), [changes.list scopes](https://developers.google.com/workspace/drive/api/reference/rest/v3/changes/list).

Desktop uses system-browser code+PKCE S256, per-attempt random state/verifier, loopback-only short-lived callback and exact transaction validation. Store refresh credentials in OS secure storage; unavailable/locked storage yields session-only or reconnect, never plaintext fallback. Android uses GIS `AuthorizationClient`, appropriate package/signing registration, SDK token acquisition and a native worker bridge; no desktop callback transplant, backend secret or on-device server refresh-code flow. A background worker needing user resolution pauses for foreground reconnect. Native access-token handles never reach JS, sidecars, logs or manifests. [Desktop native OAuth](https://developers.google.com/identity/protocols/oauth2/native-app), [Android authorization](https://developer.android.com/identity/authorization), [credential practices](https://developers.google.com/identity/protocols/oauth2/resources/best-practices).

Account identity comes from authenticated `about.get(fields=user(permissionId,displayName,emailAddress),storageQuota)` and is project+permissionId; clientRegistrationId remains separate so Android/desktop can share identity. Revalidate before resuming jobs after auth. Account switch cancels leases, increments generation and hides prior account views; callbacks cannot retarget A's queue to B. Local disconnect, offline work retention, and project-wide revoke are distinct explicit actions; failed revoke stays incomplete. No automatic importing of the current global settings into a newly connected account. [about.get](https://developers.google.com/workspace/drive/api/reference/rest/v3/about/get).

Picker desktop/mobile flow uses only drive.file, its documented browser trigger/consent flow and returned picked IDs; Android opts out of including prior scopes for that request. Enable Picker API. A selected existing photo remains external unless user chooses Copy into RapidRAW. Folder selection alone is not an access guarantee. [Native Picker, updated 2026-10-12](https://developers.google.com/workspace/drive/picker/guides/desktop-mobile-picker).

Uploads use immutable staged sources and resumable sessions; sessions/URLs stored protected natively, never ordinary queue JSON. Chunk size 1 MiB (multiple of 256 KiB); query acknowledged offset after interruption. Handle session expiry and ambiguous completion using the pre-generated file ID and exact metadata/hash reconciliation. Treat 409 as evidence to inspect, not unconditional success. Retry only transient network/rate/server failures with full jitter, exponential 1–64s ceiling, maximum eight automatic attempts per burst then visible paused retry; honor Retry-After. Auth/quota/input errors have distinct actions. [Uploads and pre-generated IDs](https://developers.google.com/workspace/drive/api/guides/manage-uploads).

Downloads use native streaming `alt=media`, capability checks, temporary files and content verification before atomic promotion. Resume only a matching version/range; changed source discards the partial, never appends to mixed bytes. Compare pre/post remote metadata; expected manifest SHA-256 is final authority for sync assets. First external-original download computes its own hash but cannot claim equality to an unseen camera original. Thumbnail URLs are short-lived; native fetch validates approved Google hosts/redirects, never forwards credentials to arbitrary hosts, honors cache headers and only exposes local cache handles. ## 7. Resource policy and export boundary

Provisional measurable defaults, **not measured throughput or RAM promises**: one bulk transfer and one metadata request at a time; at most two thumbnail requests; 1 MiB streaming buffer per bulk transfer, no whole-photo/base64 IPC. Prioritize small saved state/checkpoints before library blobs and originals. Pause bulk background work during interactive RAW decode/export. Limit JSON manifests to 1 MiB each, parsed nesting32, 256 dependency refs, 10,000 indexed revision headers per reconciliation batch; hitting a bound yields explicit ResourceLimit/continue pagination, never silent omission or forced pruning. Large masks/profile bytes are blobs. Initial per-asset library cap64 MiB, per-photo/export cap512 MiB; oversize remains a visible unsupported-policy job pending a separately measured limit increase.

Cache defaults: Android clean originals512 MiB + thumbnails64 MiB; desktop originals2 GiB + thumbnails128 MiB, LRU clean entries only. Durable edits/profiles/queued outputs are separate and counted visibly. Before staging reserve required remaining bytes plus 256 MiB headroom; unknown content length requires an explicit bounded size cap, not unchecked growth. Disk reserve/limits are tunable device-local. Dirty/open/queued data cannot be evicted to make a number green; stop download and explain storage need. Enrolled profile libraries download on unmetered connection after user enables that category; originals only on Open/Keep local. Metered bulk sync requires explicit opt-in; small settings/edit metadata may sync on metered after the category consent. A dirty editor must have an explicit durable local-working-copy decision before provider-cache expiry; do not silently extend expiring provider cache because it is pinned. Never erase local edits when clean cache expires. Cache expiration is the earlier of applicable provider headers or provisional24h thumbnail/7d clean-original policy; explicit local working copies are distinct and subject to the policy gate above.

The [current checkpoint notes](../releases/1.6.27.md) do not establish a representative RAW transfer benchmark. Device free-space/transfer-memory/long-job measurements are missing. Do not extrapolate host build-disk reserves into phone settings. WorkManager constraints and Android16+ job quotas mean no guaranteed continuous background transfer; evaluate user-initiated transfer jobs separately.
